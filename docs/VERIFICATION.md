### 건축주 시점 점검 4차: 구매 비교와 모델 연결 (같은 PR, 로컬)

구매 비교는 kg당 단가만 계산해 “이 모델을 뽑는 데 재료비가 얼마인가”에 답하지 못했습니다. 형상 점검의 재료 상한(g)을
숫자로 함께 저장하고, 구매 비교에 현재 모델 재료비 상한 열과 설명을 추가했습니다. 결과 카드의 재료 항목에서 바로 이동합니다.

실제 앱에서 120 × 80 × 35 mm 수납함(약 55.9 g) 생성 → “구매 비교에서 재료비 보기” → 상단 안내 → 세 상품 비교:
5 kg ₩95,000 상품 약 ₩1,062, 1 kg ₩32,000(배송 포함) 약 ₩1,789, 배송비 미확인 상품은 “배송비 제외 금액”으로 표시했습니다.
이 회차에서 바로 앞 브라우저 사례가 모바일에서 계획 응답 전에 확인 대화를 검사하던 경쟁 조건을 찾아, 응답을 기다린 뒤
확인하도록 고쳤습니다(연속 2회 통과).

자동 검사: Python **687개**, UI 상태 **202개**, Chromium **76개** 통과.

### 합성 프린터로 확인한 실제 화면 흐름

`scripts/fake_bambu_printer.py`(테스트 전용 인증서를 쓰는 **합성** 프린터)와 실제 앱 서버를
실행하고 앱 브라우저에서 직접 조작했습니다.

1. **4초 동안 찾기**: 합성 프린터의 SSDP 알림이 실제 서버의 수신 소켓으로 들어와 `P1S (C12) · 127.0.0.1 ·
   01S00SYNTH000001`로 표시되고, 선택 시 IP·시리얼이 채워졌습니다.
2. 틀린 코드: `access_rejected`로 표시되고 출력 값은 표시하지 않았습니다.
3. 맞는 코드: 출력 중, 진행률·남은 시간·레이어·노즐/베드 온도, HMS `0700_8000_0002_0001`, AMS 재료 2개가
   표시되고 인증서가 고정됐습니다.
4. 합성 프린터를 다른 인증서로 재시작한 뒤 다시 읽기: `certificate_changed`로 중단됐고, 합성 프린터 로그에
   CONNECT가 **기록되지 않아** 액세스 코드가 전송되지 않았음을 확인했습니다.
5. 서버 로그에 입력한 두 액세스 코드 문자열이 **0회** 나타났습니다.

캡처 동안만 기존 HTML `hidden` 속성으로 상단 메뉴·본문 건너뛰기 링크를 숨겼다가 복원합니다.
CSP를 완화하거나 inline style을 추가하지 않습니다. 컴포넌트 캡처 여섯 개의 확인이며,
상단 메뉴를 포함한 전체 페이지·수치로 측정한 대비·실물 휴대전화 검증은 아닙니다.
새 PNG 12개의 파일 무결성 검사와, 그중 여섯 개를 직접 본 범위도 구분합니다.

출력 메모의 임시 보관은 현재 브라우저 화면의 메모리입니다. 브라우저 종료·새로고침 전에
원래 작업에 저장하거나 복사해야 하며, 전체 백업에 미저장 메모가 포함된다는 뜻은 아닙니다.
수정 기록은 가장 최근에 적용한 변경안이며 전체 대화 이력이 아닙니다.

### 브라우저에서 발견해 수정한 수치 정규화 문제

첫 구현 [`f91aab4`](https://github.com/uulab-official/3d-printer-agent/commit/f91aab459a80e7bc22129d977d8c425fa651c5db)의
[CI 43694011874](https://github.com/uulab-official/3d-printer-agent/actions/runs/43694011874)은
기존 흐름 등을 포함한 48개가 통과했지만 새 수정 흐름 두 개에서 실패했습니다.
Python의 길이 변경값 `5.0`이 브라우저 JSON을 거쳐 `5`가 되면서 검토 해시가 바뀌었습니다.
이전 설치·native 성공을 조합해 릴리스하지 않았습니다.

모든 길이 값은 해시 계산 전에 같은 부동소수 표현으로, 음수 0은 양수 0으로 정규화합니다.
개수는 엄격한 정수로 유지하며 원래 숫자·형상 검사와 저장 기록의 정확한 재계산 검증을
완화하지 않습니다. 실제 Node JSON 직렬화와 음수 0 부모를 포함한 CAD API 회귀를 추가해
실패를 재현한 뒤 수정했습니다. 이후 브라우저에서는 수치·기록 일치와 다운로드 형상 검사가 통과했습니다.
개발용 전체 Python 테스트는 Node.js 22 이상이 필요하며 앱 실행에는 Node가 필요하지 않습니다.

### 이력 목록의 수정 기록 전달 보완

두 번째 소스 [`0975fa4`](https://github.com/uulab-official/3d-printer-agent/commit/0975fa4520b6511ec0fdbf7b6237b144999e8f9e)의
[CI 43694957950](https://github.com/uulab-official/3d-printer-agent/actions/runs/43694957950)에서도
48개가 통과하고 두 수정 흐름은 이후 이력 표시 단계에서 실패했습니다. 원래 작업·manifest에는
수정 기록이 있지만 SQLite의 목록 요약에는 없어 화면에 전달되지 않았습니다.
실제 trace의 목록 응답과 저장된 화면 상태에서 같은 누락을 확인했습니다.

목록은 현재 페이지에 표시할 작업만 같은 저장소 잠금 아래에서 읽고, 검증한 수정 기록만
덧붙입니다. 기존 여섯 요약 필드·정렬·커서는 유지하며, 손상·누락된 작업은 고정된 읽기 오류로
표시합니다. DB 변경·전체 이력 스캔·부모 재귀 조회·모델 파일 재읽기는 하지 않습니다.
페이지마다 추가 파일 읽기가 생기며 대규모 이력의 지연 시간을 인증한 것은 아닙니다.

실제 저장/API 회귀 5개로 실패를 재현해 수정하고, 설치 검사에는 생성 직후·재시작 후·복원 후
정확히 하나의 자식 기록과 전체 수정 기록이 일치하는 세 검사를 추가했습니다.
운영체제마다 생성 직후 4개·재시작 후 5개·복원 후 5개 목록 항목을 보관하며, 세 운영체제의
응답 본문 9개에서 기존 여섯 요약 필드와 선택적 수정 기록·정렬·기존 작업의 기록 생략을 대조했습니다.
이 세 검사 없이 게시하지 않는 조건도 회귀로 검증했습니다. 실제 목록 응답을 JSON으로
다시 직렬화해 보관하며, 그 구조·값을 독립 대조한 결과와 원래 HTTP wire 바이트를 구분합니다.
독립 검토를 거친 최종 `62317af`에서 세 workflow를 모두 다시 통과시켰습니다.

### 실제 native 회귀와 남은 진단

기존 네 합성 경로의 새 산출물 재검사는 **251개(독립 데이터 238개 + CI 기록 일관성 13개)**를

이 값의 물리적 정확성은 검증하지 않았습니다. G-code의 필라멘트 체적 단위 표기도 검증하지 않았습니다. 이를 출력 시간·재료

제작안 수정 흐름의 브라우저·설치 검증과 구분합니다. 실제 사용자 GUI 프로젝트·프린터·실물
출력과 다른 native 운영체제·버전은 검증하지 않았습니다.

### 공개 전 발견해 수정한 문제

- 검증한 CAD의 경로를 다시 읽는 동안 다른 바이트가 들어갈 수 있는 경계를 고쳤습니다. 검증한 바이트를 준비 함수에 직접 넘기고 영수증의 모델 해시를 저장된 CAD와 대조합니다.
- 손상된 필라멘트 저장 입력을 정상 복원 응답으로 돌려주지 않도록 읽기 검증을 추가했습니다. UI도 전체 입력을 검증한 뒤 한 번에 복원합니다.
- 보관함의 항목 선택이 바뀐 뒤 늦은 열기 응답이 끝나도 대기 상태가 남는 문제를 재현·수정했습니다. 응답 적용 조건과 요청 자체의 대기 해제를 분리했습니다.
- [앞선 CI 43689167120](https://github.com/uulab-official/3d-printer-agent/actions/runs/43689167120)은 기존 42개만 통과하고 새 4개에서 캡처용 inline style이 CSP에 막혔습니다. 정확히 의도한 409·422 등록도 보완했습니다. 제품 CSP와 전체 오류 검사, 시나리오 assertion은 유지했습니다.
- 테스트만 바꾼 `34b5fd6`에서는 native push 경로 필터 때문에 세 검증을 같은 소스로 맞출 수 없었습니다. native의 main push 경로 필터만 제거해 세 workflow의 실행 조건을 맞췄습니다. PR 필터·브랜치 제한과 동일 소스·최신 실행 차수·성공 여부를 요구하는 게시 규칙은 유지했습니다.

앞선 성공/실패 산출물을 최종 소스의 결과로 섞지 않았습니다. 별도 코드 검토와 수정 검토를
거친 `020b552`에서 모든 실행과 파일 검증을 다시 수행했습니다.

파일과 재사용한 로컬 의존성은 배포 wheel이나 세 운영체제 검증의 근거로 사용하지
않습니다. 로컬 Chromium/native 실행 제약을 재시도하거나 우회하지 않았으며 실제
실행 근거는 위 GitHub CI와 내려받은 산출물입니다.

### 여섯 설정의 실제 브라우저 흐름

새 두 시나리오가 기존 19개 시나리오와 함께 두 화면 크기에서 실행됐습니다.
첫 흐름은 지원하는 합성 Studio 프로젝트 가져오기 → 여섯 항목 편집 → 원본과 차이
검토 → 명시적 변경 기록 생성 → 현재 CAD 준비 → 원본·CAD·변경 프로젝트 다운로드
→ 실제 서버 재시작 → 저장 이력 열기 → 변경 기록 재검증과 명시적 선택 → 새 준비입니다.
원본은 **7 × 7 × 7 mm 큐브**, 현재 CAD는 **127 × 80 × 35 mm**이며 준비 파일의
모든 정점·삼각형이 현재 CAD와 같습니다. 원본의 객체별 설정과 G-code는 옮기지 않습니다.

브라우저 산출물의 독립 검사는 **176개**를 통과했습니다. 외부 ZIP의 크기·해시와
554개 항목의 실제 바이트, 소스 커밋·실행 ID와 42개 단일 성공 결과를 대조했습니다.
두 화면 모두 실제 내려받은 설정 612개에서 **정확히 여섯 개만 바뀌고 606개는 유지**됩니다.
전체 설정을 원본과 입력값으로 다시 구성하고 검토 해시·원본/설정/CAD 해시·변경 기록
ID·3MF 메타데이터·모든 준비 파일 영수증을 재계산했습니다. 처음 준비한 파일과 이력
재검증 뒤 새로 준비한 파일은 바이트가 같고 준비 폴더는 다릅니다. 최초/재시작 후 이력
HTTP 본문, 저장/재검증한 변경 기록 본문과 새 준비·이력 본문도 함께 보관해 대조했습니다.

복구 흐름에는 실제 HTTP 200/422 검토 응답과 201 생성 응답을 보류한 뒤 새 입력·취소를
하는 경우, 정확한 공백·미완성 소수 입력, 새 원본 후보의 유지/교체 선택, 별도 수동 JSON과
재료 초안 보존이 포함됩니다. 취소 후 늦게 생성된 기록은 이전 적용 기록과 구분되며
선택되거나 자동 재전송되지 않습니다. 실제 로그는 두 서버 PID와 종료/재시작, 변경 기록
재검증 뒤 명시적인 새 준비를 보여 줍니다. **자동 재전송이 없다는 검사는 변경 기록 생성과
슬라이싱 요청에 대한 것**입니다. 이전 세션을 시험하는 discovery POST의 의도된 403과
나중에 직접 실행한 slice POST의 200까지 없었다고 주장하지 않습니다.

지연 응답의 실제 전달 시점, 취소 클릭과 후보 유지/교체 동작은 성공한 CI assertion과
보관한 HTTP 본문·로그로 뒷받침합니다. 전체 브라우저 프로토콜 trace가 없어 모든 클릭
시점을 산출물에서 독립 복원했다고 표시하지 않습니다. 기존 19개 시나리오는 두 화면에서
성공하고 첨부 바이트도 확인했지만 기존 의미 검사를 모두 새로 독립 감사한 것은 아닙니다.

검토·적용·이력 선택·잘못된 초안·재연결을 보여 주는 컴포넌트 스크린샷 **12개**를
직접 확인했습니다. 데스크톱 2열·모바일 1열 입력, 단위·원본 값, 비활성화한 잘못된 값의
적용 버튼과 변경 전후를 확인했습니다. 일부 데스크톱 제목과 모바일 차이 제목에는 고정
상단 메뉴가 겹치고, 긴 모바일 편집 캡처에는 초점이 있는 본문 건너뛰기 링크가 겹칩니다.
가림 없는 전체 페이지 캡처나 실제 휴대전화 검증으로 확대하지 않습니다. 이 브라우저
흐름의 native 실행 값은 `null`이며 실제 Studio 슬라이싱은 다음의 별도 근거입니다.

### 실제 설치 패키지의 재시작·백업·복원

배포 wheel은 **187,976바이트**, SHA-256은
`862ba6c21f7d7dcb24489a802d2fd3358002b727f166a34bee334cf56846afdf`입니다.
Ubuntu 24.04 x86_64, macOS 15 arm64, Windows 2025 AMD64가 같은 wheel을 설치하고,
각각 183개 실제 검사에 통과했습니다. wheel의 앱 파일 **24개**는 커밋된 소스 바이트와
모두 같습니다. 독립 산출물 검사는 **265개**를 통과했습니다.

기존 원본 설정을 사용하는 케이블 CAD 사례를 유지하면서 세 번째 모델에 여섯 합성
변경값을 검토·적용했습니다. 실제 다운로드에서 원본 전체 설정과 여섯 명시적인 변경값으로
적용 설정을 재구성하고, **65 × 65 × 7 mm의 현재 인셋 프레임 CAD**의 정점 530개와
삼각형 516개의 모든 좌표·연결을 대조했습니다. 준비/이력/묶음/영수증과 재시작 후 기록도
일치합니다. 원본 설정 JSON 값과 변경 후 canonical JSON은 세 운영체제에서 같습니다.
Windows 원문은 줄바꿈 표현이 달라 원문 해시가 다르며, 전체 준비 파일도 원본·기록 ID
등이 달라 운영체제 사이에 바이트가 같다고 표시하지 않습니다.

각 백업은 원본, 변경 기록, CAD, 기존 초안과 준비 파일을 포함한 **36개 파일**입니다.
모든 파일의 실제 바이트를 manifest·원본 폴더·기록된 복원 전 목록과 대조했습니다.
새 폴더에 복원한 서버에서 같은 변경 기록 ID를 읽고 **복원된 폴더의 경로로 새 준비**를
수행합니다. 각 운영체제 안에서는 이 새 준비 파일이 이전 변경 프로젝트와 바이트가
같습니다. 원본 폴더는 변하지 않으며, 복원된 폴더에만 이후 새 준비와 손상 파일 시험이
추가됩니다. 따라서 마지막 복원 폴더가 복원 직전 스냅샷과 영원히 같다고 주장하지 않습니다.

설치된 `site-packages`의 실제 바이트 비교와 STEP solid 유효성은 소스 해시를 확인한
CI 스크립트의 실행 결과입니다. 내려받은 wheel과 커밋, 저장된 3MF XML·해시·백업 바이트는
독립 재계산했지만 설치 환경이나 CAD 엔진을 이 검토에서 다시 실행하지 않았습니다.

### 독립 검토에서 수정한 문제

공개 전 코드 검토에서 손상된 변경 이력이 원본만 선택하는 경로로 바뀔 수 있는 UI 문제를
재현했습니다. 수정 후 손상 이력 12가지에서 원본 조회·쓰기 없이 적용이 차단되고, 정상 원본/
변경 이력 두 가지가 올바른 읽기 경로와 명시적 선택을 사용하는 것을 확인했습니다. 설치
스크립트가 핵심 30개 설정과 전체 612개 설정을 잘못 비교하는 오류도 수정하고 두 독립
비교를 유지했습니다. 순수 편집 엔진은 여섯 항목의 모든 **64개 부분집합**에서 원본·미변경값·
변경 기록 재계산을 독립 대조했습니다. 모든 scoped 검토와 최종 전체 변경 검토를 통과한
소스를 게시했습니다.

### 앞선 실패와 수정의 기록

별도 진단 브랜치 `519f7b5fae9a23743b8e983a92aed3060765dcac`의
[실행 43597797224](https://github.com/uulab-official/3d-printer-agent/actions/runs/43597797224)는
전체적으로 **실패**했습니다. 새 Application 이름을 정직하게 기록한 probe가
native 종료 `-11`과 출력 없음으로 실패했고, 공급된 원본 표시를 유지한 probe만
설정·새 메시·G-code 검사를 통과했습니다. 이 진단을 성공한 workflow로 바꾸어
기록하지 않습니다. 결과에 따라 원본에 실제 있던 지원 표시만 유지하고 수정자와
원본·모델 해시를 따로 기록했습니다. 외부 형식에 Bambu 표시를 만들어 넣지 않습니다.
위의 최종 production CI는 이 진단과 별도로 실제 앱 경로를 통과한 실행입니다.

게시 전 독립 검토에서 다음 실제 반례를 수정하고 회귀 검사를 추가했습니다.

- native 설정의 값 표현과 `project_settings` 식별을 확인하지 않던 경계.
- 보관 원본 누락을 HTTP 500으로 반환하던 경로: 과거 결과를 해제하고 404를 반환.
- 미지원 ZIP 추출 버전이 예외로 빠지던 경로: 부분 원본을 남기지 않고 HTTP 422로 거절.
- 공유 artifact 처리에서 명시적 `null` 해시가 오래된 영수증 없음과 같게 취급되던 회귀.

컨트롤러의 미완료 Promise가 성공 종료로 보이지 않도록 검사 하네스에도 제한을
추가했습니다. 재료·구매 요청의 규칙 분기는 LLM 설정 확인과 호출보다 먼저 실행해
두 모드에서 같은 화면으로 안내합니다. 일반 CAD는 선택한 엔진을 유지하며,
실제 외부/로컬 LLM 서버를 호출한 검증은 아닙니다.

솔리드이며, 독립 3MF 좌표 계산으로 다음 치수를 확인했습니다.

재계산한 값과 일치합니다. 플랫폼 스크립트 해시가 모두 같다고 주장하지 않습니다.

### 실제 브라우저의 중단·복구·이력

새 흐름은 실제 Python 서버를 재시작해 만료된 세션의 HTTP 403을 확인하고,
명시적인 재연결 후 숫자 입력 `-`, 요청 문장, 미완성 필라멘트 JSON을 보존합니다.
서버에서 실제 CAD 생성이 끝난 성공 응답을 지연시킨 상태에서 먼저 재연결하고,
늦은 응답이 현재 화면을 바꾸지 않으며 작업 기록에서 별도로 열 수 있음을 확인합니다.
CAD 생성은 대역으로 바꾸지 않았고, 재연결 중 변경 요청을 자동 재전송하지 않습니다.

다른 흐름은 실제 CAD 하나에 합성 실패 102개·중단 하나·읽을 수 없는 기록 하나를
추가한 뒤 서버를 재시작합니다. 유효 기록 104개, 중단 처리 1개, 읽기 확인 1개가
표시되고 페이지를 이어 읽어 총 105개 중 가장 오래된 실제 CAD를 엽니다.
목록 실패 복구 검사에는 지연한 실제 응답과 명시적인 합성 HTTP 503을 사용합니다.
오래된 실패가 새 목록을 덮지 않으며, 현재 새로고침 실패도 기존 목록을 지우지 않습니다.

새 브라우저 산출물의 독립 검사 **54개**에서 복구된 모델의 실제 3MF 해시와
90 × 60 × 18 mm 치수, 원본 출처, 부분 결과 부재, 이력 복구 기록을 확인했습니다.
브라우저가 저장한 job/manifest JSON 스냅샷은 재직렬화되어 `90.0`을 `90`으로
표현하므로 원본 바이트라고 취급하지 않았습니다. 스냅샷의 값은 원래 작업 파일과
비교하고, 설계 해시는 원래 JSON으로 재계산했으며 manifest 원본은 별도 저장된
바이트 영수증과 대조했습니다. 이 구분 없이 스냅샷에서 해시를 다시 계산하던 초기
검사기의 실패는 해당 검사기만 바로잡았습니다. 제품 코드를 변경한 실패는 아닙니다.
기존 추천·출처·다운로드 흐름에도 새 산출물로 **57개**의 독립 회귀 검사를 적용했습니다.

데스크톱·모바일에서 각각 연결 만료, 재연결, 시작 복구, 모델 교체 확인, 오래된
CAD 카드의 스크린샷을 확인했습니다. 총 10개 구성 요소 이미지에서 주요 버튼과
경로·설명 문구가 잘리지 않았습니다. 긴 저장 경로는 작은 화면에서 줄바꿈됩니다.
전체 페이지 시각 검사, 색상 대비 측정, 실물 휴대폰 검증으로 확대하지 않습니다.

### 실제 실행으로 발견한 추가 계약

첫 앱 어댑터 실행 [43375168823](https://github.com/uulab-official/3d-printer-agent/actions/runs/43375168823), 커밋 `d0a67c16d8366ab2fdda14e920893fbaffa64fd6`은 STL·3MF 모두 native 종료 코드 239, 내부 코드 -17로 실패했습니다. 어댑터는 두 결과를 `failed`로 반환하고 출력 파일·해시를 성공 결과로 승격하지 않았습니다. 원인은 합성 machine의 `from: "user"`에 시스템 부모가 없고 process에 명시적 호환 목록이 없었던 것입니다.

고정한 upstream 소스에서 이 동작을 확인했습니다. CLI는 `from: "system"`인 machine에는 `name`을 시스템 이름으로 사용하고, user machine에는 `inherits`를 사용합니다. 새 process의 `compatible_printers`가 해당 이름과 정확히 일치해야 합니다. 이에 따라 현재 지원하는 해소된 루트 구성의 계약을 명시하고, 사용자 machine 계보·누락 또는 불일치한 process 호환 목록을 준비 단계에서 설명과 함께 차단합니다. 사용자 파일의 `from`이나 상속·호환 목록을 자동으로 바꾸지는 않습니다.

별도의 합성 CI fixture에는 명시적인 native 루트 분류와 그 이름을 참조하는 process 호환 목록을 사용합니다. 이 분류는 제조사 출처를 뜻하지 않으며, 실제 provenance는 합성 입력으로 기록합니다. native 기본값에 의존하는 최소 설정이라 실제 장비용 추천 프리셋으로 배포하지 않습니다.

독립 코드 검토에서는 출력 설정의 1,200단계 배열이 재귀 비교에서 오류를 일으키고, 64단계의 비정상 래핑이 정상값으로 비교되는 문제를 재현했습니다. 디코딩한 설정의 컨테이너 깊이를 32로 제한하고 JSON 파서의 재귀 오류도 처리했습니다. 손상된 입력 프로젝트 설정은 준비 전에 차단하며, 손상된 출력 설정은 `needs_review`로 반환합니다. 선택 플레이트의 온도 0이 native에서 미지원 조합을 뜻하는 규칙도 확인해 준비 단계에서 거절하고, 미선택 플레이트의 0은 보존합니다.

3. 다른 탭의 저장을 실제 API로 재현 → 오래된 revision의 저장은 409 → 현재 편집 유지 → 별도 복사본 저장 → 복사본의 저장본만 삭제하고 현재 입력과 다른 탭의 저장본은 유지.

각 흐름을 데스크톱과 모바일 화면에서 실행했습니다. 첫 두 흐름은 하나의 연속 테스트에 들어 있으므로 프로젝트당 새 테스트는 2개입니다. API나 CAD 결과를 가짜 응답으로 대체하지 않았습니다.

브라우저가 내려받은 workspace 보고서 2개를 다시 읽었습니다. 부모 원본과 현재 문서가 같고, 원래 자식에는 없던 유량 필드만 편집본에 추가되며, `inherits`와 원래 검증 메타데이터가 보존됨을 확인했습니다. `validation_status`는 `stale`, `can_prepare_profile`은 `false`였고 변경 필드는 정확히 하나였습니다. 원본과 편집본의 모든 canonical SHA-256을 별도로 계산해 보고서와 대조했습니다. 장비 조건 8개도 보존됐습니다.

독립 코드 검토에서 다음 두 문제를 재현하고 수정했습니다.

- 저장본을 여는 중에 선택한 파일이 늦게 읽히면 앞선 열기 응답이 그 파일을 버리는 경쟁 상태. 파일 선택을 시작한 시점부터 새 편집으로 기록해 앞선 열기가 덮어쓰지 못하도록 했습니다.
- 큰 원본의 편집본을 줄인 뒤 다른 파일을 추가하면 원본 합계가 2 MiB를 넘어도 가져오기가 성공하는 문제. 편집본과 보관할 원본의 한도를 각각 검사하고, 실패 시 기존 원본과 초안을 유지합니다. 붙여 넣은 JSON을 원본으로 채택할 때도 같은 제한을 적용합니다.

단위 검사에는 서로 독립적인 SQLite 저장 인스턴스의 동시 수정 경쟁, 오래된 revision의 수정·삭제 거절, 앱 재시작, 미완성 문자열 보존, 숫자 표현 유지, JSON 깊이·크기·안전한 정수 경계, 늦은 저장·열기·파일 읽기 응답, 원본 키 순서만 바뀐 경우의 비교가 포함됩니다.
